# Тара+ - сайт расчёта деревянной тары по ГОСТ (серверная версия)

Сайт «Тара+»: расчёт дощатых ящиков по ГОСТ 10198-91 (типы I-1, I-2, I-3,
I-4, II-1, II-2, III-1) и ГОСТ 2991-85 (типы I и II-1 - в работе) - таблица деталей, чертежи узлов, объём
пиломатериала, масса ящика, нормы времени, печать и PDF. Расчётные формулы
выполняются на сервере (Node.js + Express, `backend/`), страницы - в
`frontend/public/`. Здесь же аккаунты, подписки и лимиты, администрирование,
заявки на внутренние стандарты заводов и сообщения об ошибках.

Статическая версия калькулятора (репозиторий
[`pakhiton79-bit/GOST_10198-91`](https://github.com/pakhiton79-bit/GOST_10198-91),
расчёт в браузере) - отдельный независимый проект: код между ними не
связан и не синхронизируется.

Как читать код: расчёт каждого типа - `backend/src/<тип>/compute.js` (точка
входа, шаги расчёта по порядку) и файлы узлов ящика рядом; вывод
результата на странице - `frontend/public/js/<тип>/render-*.js`, чертежи -
`frontend/public/js/<тип>/diagrams/`. Имена вида `t12`, `k41`, `l19` - номера
ячеек исходной таблицы Excel, см. «Словарь обозначений» в конце.

## Запуск локально

```
cd backend
npm install
npm start
```

Сервер поднимается на `http://localhost:3000` (порт настраивается переменной
окружения `PORT`) и сразу отдаёт и API, и фронтенд — открывайте
`http://localhost:3000/index.html`.

## API

### `POST /api/i3/calculate`

Тело запроса:
```json
{
  "variant": "skid",
  "L": 3000, "W": 1200, "H": 1000, "MASS": 3000,
  "optimizeSizes": false, "removeFloorBoards": false, "removeSkidBoards": false,
  "roundBoardWidths": false, "solidRigidBase": false, "forkliftLoading": false,
  "availableThicknesses": []
}
```
`variant` — `"skid"` (крепление за полозья) или `"floor_boards"` (крепление
к доскам дна). Ответ — объект с итоговыми размерами/объёмом/нормой времени,
таблицами деталей (`dno`, `kryshka`, `endPanel`, `bokovoy`) и параметрами для
отрисовки чертежей, либо `{"error": "..."}`, если входные данные не прошли
проверку по ГОСТу. `"addRaskosina": true` (I-3 и I-4) - раскосины в торцевом и
боковом щитах всегда, независимо от ГОСТ (по ГОСТ - только в щитах выше
600 мм, торцевой - ещё и шире 600 мм); угол вне 20-60° - предупреждение, при
одном поясе планок крышки у бокового щита раскосину ставить некуда.

### `POST /api/i1/calculate`

Тело запроса:
```json
{
  "L": 2000, "W": 1000, "H": 900, "MASS": 500,
  "skidEnabled": true, "skidThicknessRaw": 50,
  "roundBoardWidths": false, "availableThicknesses": []
}
```
Ответ — аналогичный объект с таблицами `dno`/`kryshka`/`bokovoy`/`torec`.

### `POST /api/i2/calculate`

Тело - как у I-1 (кроме `addParchment`: пергамина у I-2 нет) плюс `"boardGapPercent": 25` (доля промежутков между
досками обшивки, 10-50%; без неё - ошибка). В ответе дополнительно
`boardGaps`: по щитам `{ qty, gap, share }` или `null` (промежутки не вышли,
щит сплошной - об этом предупреждение).

### `POST /api/i4/calculate`

Тело - как у I-3 (кроме `addParchment`: пергамина у I-4 нет) плюс
`"boardGapMax": 60` (наибольший промежуток между досками обшивки, 10-100 мм;
без него - ошибка): доски по 100 мм, крайние - по краям щита, остальные
равномерно, их наименьшее число, при котором промежуток не больше заданного. В ответе
дополнительно `boardGaps`: по щитам (`dno`,
`kryshka`, `torec`, `bokovoy`) `{ qty, gap, share }` или `null` (щит сплошной -
промежутки не вышли, об этом предупреждение; у дна - и когда доски убраны).

### `POST /api/ii2/calculate`

Тело - как у II-1 (кроме `addParchment`: пергамина у II-2 нет) плюс
`"boardGapMax": 100` (наибольший промежуток между досками обшивки, 10-150 мм;
без него - ошибка): доски по 100 мм, крайние - по краям щита, остальные
равномерно, их наименьшее число, при котором промежуток не больше заданного.
Конструктив - как у II-1: доски бока - на длину груза + 2 толщины стойки
торцевого щита, доски торца - по наружной ширине. При досках крышки поперёк
доски бока продолжают линии досок крышки: крайние доски бока уже 100 мм на
толщину обшивки торца («Доска (крайняя)», в `boardGaps.bokovoy` - `cut`). В ответе
дополнительно `boardGaps`: по щитам (`dno`, `kryshka`, `torec`, `bokovoy`)
`{ qty, gap, share }` или `null` (щит сплошной; у дна - и когда доски
убраны).

### `POST /api/iii1/calculate`

Тело - как у II-1 (кроме `fineThickness`), включая `"bulkCargo"` (насыпной или
незакреплённый груз: обшивка 19 мм вместо 16) и `"addRaskosina"` (раскосины и
при высоте до 600 мм). В ответе дополнительно `bolts`: строки болтов
`{ name, d, qty }`.

### `POST /api/g2991i/calculate`

ГОСТ 2991-85, тип I. Тело - как у II-1, без `verticalEnd`. Ответ - как у
II-1 (без планок торца).

### `POST /api/g2991ii1/calculate`

ГОСТ 2991-85, тип II-1. Тело: `L`, `W`, `H`, `MASS`, `species` (`conifer` /
`birch` / `softDeciduous`), `concentrated`, `packet`, `noLid`, `verticalEnd`,
`roundBoardWidths`, `availableThicknesses`, `availableWidths`, `mainWidth`
(основная ширина доски, выбор внутри типа, по умолчанию 100; вверх до ширины
«в наличии»), `tableEdits`, нормы времени и
плотность. Ответ: `dno`, `kryshka`, `torec`, `bokovoy` (строки деталей),
`thickness`, наружные размеры, `totalVolume`, `crateMass`, `normaVremeni`,
`warnings`.

## Аккаунты (этап 1)

Почта + пароль, код подтверждения на почту при регистрации и при
восстановлении пароля (`backend/src/auth/`, страница `login.html`). В верхней
панели - «Войти» и «Регистрация» для гостей, у вошедших - кнопка с почтой,
открывающая «Настройки» на разделе «Аккаунт»; всё об аккаунте (почта,
выход, устройства, удаление, подписка и лимиты) - в окне «Настройки»,
разделы «Аккаунт» и «Подписка» (`js/common-account.js`). Старая ссылка
`account.html` открывает главную сразу на разделе «Аккаунт». Если вход
завершился, пока страница открыта, панель переключается на «Войти» с
пояснением; сбой связи с сервером выходом не считается (повторы запроса).

- Хранилище - JSON-файл `backend/data/accounts.json` (каталог можно задать
  переменной `DATA_DIR`; в git не попадает). На бесплатном Render файл
  стирается при каждом перезапуске и деплое - аккаунты пропадают (временно
  допустимо, до переезда на свой сервер с базой данных).
- Пароли - scrypt с солью; вход - cookie `sid` (HttpOnly, 30 дней), на
  сервере хранится только хэш токена.
- Коды - 6 цифр, 15 минут, 5 попыток, новый код - не чаще раза в минуту.
- Почта - через Unisender Go по HTTP API (`backend/src/auth/mailer.js`; на
  бесплатном Render почтовые порты SMTP закрыты). Уходят коды подтверждения
  и восстановления пароля, а также заявки на стандарты и сообщения об ошибках
  на почту поддержки (ответ на такое письмо уходит пользователю). Если код не
  удалось отправить, пользователь видит «Не удалось отправить письмо с
  кодом» и может сразу запросить новый.
  Переменные окружения (Render → сервис → **Environment**):

  | Переменная | Что это |
  |---|---|
  | `UNISENDER_GO_API_KEY` | API-ключ из личного кабинета Unisender Go |
  | `UNISENDER_GO_URL` | адрес API из личного кабинета, например `https://go1.unisender.ru/ru/transactional/api/v1` (у аккаунта может быть `go2`) |
  | `MAIL_FROM` | адрес отправителя на домене, подтверждённом в сервисе (например `noreply@ваш-домен.ru`) |
  | `MAIL_FROM_NAME` | имя отправителя, по умолчанию «Тара+» |
  | `SUPPORT_EMAIL` | почта поддержки: сюда приходят заявки и сообщения об ошибках |
  | `MAIL_SKIP_UNSUBSCRIBE` | `1`, если поддержка сервиса разрешила письма без ссылки «отписаться» |

  Пока `UNISENDER_GO_API_KEY` или `MAIL_FROM` не заданы - тестовый режим:
  письма не уходят, код пишется в журнал сервера (Render → сервис →
  **Logs**, строка `[почта, тестовый режим]`). Без `SUPPORT_EMAIL` заявки и
  сообщения об ошибках тоже только в журнале (и в админке).
- Запросы `/api/auth/*` (кроме `me`/`logout`) - не больше 30 за 10 минут с
  одного IP.
- Защита от ботов на регистрации и «Забыли пароль» (`backend/src/auth/antibot.js`):
  - скрытое поле-ловушка `website`: заполнено - запрос молча «принимается»,
    но аккаунт не создаётся и письмо не уходит;
  - одноразовые почтовые ящики (yopmail, temp-mail и т.п.) при регистрации
    не принимаются; дополнить список - переменная `BLOCKED_EMAIL_DOMAINS`
    (домены через запятую);
  - своя капча «Я не робот» без сторонних сервисов (данные никуда не
    передаются): браузер решает задачу сервера (`GET /api/auth/challenge`,
    перебор SHA-256, как в открытом проекте ALTCHA; `js/account/pow.js`) -
    сам, пока человек заполняет форму, около секунды на телефоне. Ответ
    одноразовый, действует 10 минут. `CAPTCHA_SECRET` (необязательно) - ключ
    подписи задач; без него - случайный при каждом запуске.

API: `POST /api/auth/register`, `verify`, `resend`, `login`, `logout`,
`forgot`, `reset`, `device-replace`, `devices/logout`; `GET /api/auth/me`,
`devices` (см. комментарий в `backend/src/auth/routes.js`).

- Вход с почтой, для которой нет аккаунта, - сообщение «Аккаунта с такой
  почтой нет» со ссылкой на регистрацию (по указанию пользователя), неверный
  пароль - «Неверный пароль».
- Пользователь может удалить свой аккаунт в «Настройки» → «Аккаунт» (с паролем).
- Администратор может заблокировать аккаунт с причиной (`admin.js`): входы на
  всех устройствах завершаются, войти и считать нельзя, причина показывается
  при попытке входа; данные аккаунта сохраняются. Разблокировка - там же.

### Безопасность

- Аккаунты хранятся в JSON-файле (`backend/src/auth/store.js`), SQL нет -
  SQL-инъекции невозможны. Все обращения к хранилищу - только через
  `store.js`, поэтому переезд на базу данных (например, при размещении на
  reg.ru) меняет один этот файл.
- Правила для будущей базы данных: запросы - только с параметрами
  (`WHERE email = $1` / `?`), никогда не склеивать SQL из строк
  пользователя; у пользователя базы, под которым работает сайт, - только
  нужные права (без DROP/ALTER); строка подключения и пароль - в
  переменных окружения, не в коде; резервные копии по расписанию.
- Тексты от пользователей (сообщения, заявки, причины блокировки) перед
  показом экранируются (`esc` в админке, `escapeHtml` в письмах).
- Cookie входа: HttpOnly, SameSite=Lax, Secure по https; API принимает только
  JSON - защита от подделки запросов с чужих сайтов.
- Заголовки (`server.js`): без X-Powered-By; X-Frame-Options SAMEORIGIN и
  CSP frame-ancestors 'self' (чужой сайт не встроит наш во фрейм, свои
  фреймы печати и PDF работают); X-Content-Type-Options nosniff;
  Referrer-Policy strict-origin-when-cross-origin; HSTS 180 дней по https.
- Лимиты: тело запроса до 100 КБ; вход и регистрация - 30 запросов за
  10 минут с IP; 5 попыток на код и не больше 15 неверных кодов за сутки на
  почту (дальше пауза до конца суток); 10 неверных паролей подряд - вход в
  аккаунт на 15 минут закрыт (восстановление пароля снимает паузу);
  сообщения об ошибках - 20, заявки на стандарты - 10 в сутки от
  пользователя, хранятся последние 2000; защита от ботов - `antibot.js`.
- Ошибки сервера посетителю - короткий текст без подробностей, подробности -
  в журнал. Пароли хешируются асинхронно (сервер не подвисает на входах).
- Аудит безопасности (07.10.2026): открыты оба репозитория на GitHub и
  статическая версия на GitHub Pages (полный калькулятор без аккаунта);
  данные на Render хранятся за рубежом и стираются при перезапуске - решить
  при переезде.
- Зависимости проверять командой `npm audit` в папке `backend` (исправление -
  `npm audit fix`).

- Цвета - только токены из `css/style.css` (светлая и тёмная тема).

## Деплой на Render

В репозитории есть `render.yaml` (Blueprint) — Render считывает его сам и
настраивает сервис автоматически, без ручного ввода полей:

1. [dashboard.render.com](https://dashboard.render.com) → **New** → **Blueprint**.
2. Подключить (или выбрать уже подключённый) GitHub-аккаунт и репозиторий
   `pakhiton79-bit/GOST_backend`.
3. Render найдёт `render.yaml` и предложит создать сервис `gost10198-91-backend`
   (Free-тариф, ветка `main`) — подтвердить **Apply**.

После этого **автодеплой уже включён**: любой `git push` в `main` сам
запускает новую сборку и выкладку — отдельно ничего настраивать не нужно.
Прогресс и логи каждого деплоя видны в Render Dashboard → сервис →
вкладка **Events**/**Logs**.

Тариф Free "засыпает" примерно через 15 минут без запросов — первый запрос
после этого поднимает сервис заново (до ~50 секунд), дальше работает быстро.

Без Blueprint то же самое можно настроить вручную (**New** → **Web Service**):
- Root Directory: `backend`
- Build Command: `npm install`
- Start Command: `npm start`
- Plan: Free

Фронтенд раздаётся тем же сервисом (Express `express.static`), отдельного
статического хостинга не требуется.

## Словарь обозначений

Часть полей ответа расчёта и ключей ручной толщины названа номерами ячеек
исходной таблицы Excel. Переименовывать их нельзя: это поля API (по ним
рисует фронтенд) и ключи, сохранённые в браузерах пользователей. Значения
для типов I-3 и I-4:

| Обозначение | Что это |
|---|---|
| `t9Value` | ручная толщина полоза |
| `t10Value` | ручная толщина подполозной доски |
| `t11Value` | ручная толщина торцового бруса дна |
| `t12Value`, `t12` | ручная толщина / толщина доски дна |
| `t21Value` | ручная толщина внутреннего поперечного бруса крышки |
| `t20`, `t30`, `t32`, `t40`, `t41` | толщина обшивки (`wall`) - для подписей разных чертежей |
| `k9Base`, `k41` | длина полоза = длина бокового щита |
| `k32` | длина доски торцевого щита |
| `k40` | длина вертикальной планки бокового щита |
| `k30plusW31` | высота этажа торцевого щита |
| `HplusT12` | высота груза + доска дна (высота щита) |
| `l19` | число поясов планок крышки |
| `l21`, `w21` | число и ширина внутренних поперечных брусьев крышки |
| `l42` | число раскосин бокового щита |
| `w43` | ширина горизонтальной планки бокового щита |

Ключи ручных толщин I-1 и I-2 названы по деталям (`tDnoBoard`, `tBokPlanka`
и т.п.), в II-1, II-2 и III-1 - свои ключи (`t9`, `t10`, `t11`, `t21` и
другие, см. `overrideKey` в узлах расчёта этих типов).
